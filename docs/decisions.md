# Продуктовые и технические решения

## 1. Исследование: чьи задачи решаем

Источники гипотез — материалы кейса, публичные описания кредитных процессов банков для МСП и типичные сценарии малого бизнеса. Интервью с пользователями в рамках хакатона не проводились; гипотезы ниже — то, что стоит проверить CustDev-интервью в первую очередь.

**Клиент** — собственник, директор, финансист или бухгалтер малого бизнеса. Банковской экспертизы у него может не быть.

| Работа (JTBD) | Боль сегодня | Что делаем в прототипе |
|---|---|---|
| Когда появился кассовый разрыв или выгодная закупка, я хочу быстро понять, какие деньги мне доступны, чтобы не упустить момент | Названия продуктов ничего не говорят: «овердрафт», «оборотный», «инвестиционный» | Путь начинается с цели («закупить сырьё»), а не с продукта; можно описать задачу своими словами; рекомендация с пояснением, почему этот продукт |
| Когда я заполняю заявку, я хочу не вводить то, что банк и так может узнать, чтобы не тратить время | Повторный ввод реквизитов, ОКВЭД, адресов | Регистрационные данные берутся из ЕГРЮЛ/ЕГРИП; клиент вводит только сумму, срок, выручку и текущие платежи |
| Когда заявка отправлена, я хочу знать, что с ней происходит и что от меня нужно, чтобы планировать | «Чёрный ящик», звонки менеджеру | Маршрут из пяти этапов, статус простым языком, явное «что дальше», живое обновление, дозапрос внутри кабинета |
| Когда банк отказал или предложил меньше, я хочу понять почему, чтобы решить, что делать | Отказ без объяснений | Объяснение решения и разбор факторов оценки; сравнение «просили — предлагаем» с платежом |

**Банк** — кредитный аналитик и риск-менеджер.

| Работа | Что делаем |
|---|---|
| Не тратить время на заявки, которые решаются по правилам | Автоматическое решение для типовых случаев, в очередь попадают только пограничные и крупные |
| По сложной заявке быстро увидеть главное | Сводка «на что обратить внимание», рекомендация системы, разложение скоринга по факторам, данные источников на одном экране |
| Объяснить и воспроизвести решение | Снимки данных, версия политики и скоринговой карты, неизменяемый журнал |
| Не терять заявки при сбоях | Очередь с повторами, деградация в ручной разбор |

## 2. Границы процесса и MVP

Процесс начинается с потребности клиента и заканчивается выдачей средств. Сопровождение кредита (погашения, реструктуризация) — за границей MVP.

Приоритизация по MoSCoW:

| | Что вошло | Почему |
|---|---|---|
| **Must** | Подбор продукта по цели, заявка, валидация, обогащение из трёх источников, скоринг, политика решения с 4 исходами (одобрение, встречное, отказ, ручное), дозапрос, рабочее место аналитика, принятие предложения, подписание и выдача (смоделированы), журнал | Без любого из этих шагов путь не сквозной — критерий «целостность решения» |
| **Must** | Docker, миграции, тестовые данные под каждый исход, OpenAPI, тесты | Критерий «готовность к проверке» |
| **Should** | Блок «Ваши заявки и предложения» (действия, события, советы), предодобренное предложение, расчёт платежа, разбор оценки для клиента | Прямо влияют на понимание клиентом своих вариантов — главный UX-риск сегмента |
| **Should** | Retry, circuit breaker, симуляция сбоев, горизонтальное масштабирование воркеров | Критерий enterprise-ориентированности, демонстрируется вживую |
| **Could** | Разбор свободного текста локальной LLM | Полезно, но путь полностью работает и без неё |
| **Won't (сейчас)** | Регистрация новых клиентов и KYC, поручители, транши, распознавание документов, реальная ЭП, уведомления вне продукта | Сложность не окупается в прототипе; уведомления вне продукта прямо запрещены условиями |

**Роли в MVP:** клиент (любой уполномоченный сотрудник компании), система, кредитный аналитик, риск-менеджер (просмотр). Отдельные роли андеррайтера, юриста и залоговой службы объединены в «аналитика» — их разделение не меняет логику конвейера и добавляется как новые переходы в машине состояний.

**Продукты:** четыре с разной экономикой (овердрафт, оборотный, инвестиционный с залогом, экспресс). Этого достаточно, чтобы показать, что один рейтинг даёт разные условия.

## 3. Ключевые технические решения

| Решение | Альтернатива | Почему так |
|---|---|---|
| Доменное ядро на чистом Python | Логика в эндпоинтах или ORM-моделях | Тестируется без инфраструктуры, переносимо, легко ревьюить кредитные правила |
| Машина состояний с правами на переходы | Свободное поле статуса | Невозможно «перепрыгнуть» этап или выполнить действие не той ролью; диаграмма генерируется из кода |
| Очередь задач в PostgreSQL (outbox + SKIP LOCKED) | Kafka/RabbitMQ | Атомарность статуса и задачи без распределённых транзакций, на одну зависимость меньше. Интерфейс воркера не зависит от брокера — заменяется при росте нагрузки |
| Шаги конвейера идемпотентны и возобновляемы | Один длинный обработчик | Падение воркера не ломает заявку, повтор безопасен |
| Polling статуса раз в 1,5 с, пока ход за банком | WebSocket/SSE | Проще, надёжнее за прокси, без состояния на сервере. При росте — SSE поверх того же журнала событий |
| Экспертная скоринговая карта | ML-модель | Объяснимость; синтетические данные не позволяют честно обучить модель |
| Фронтенд без фреймворка (TypeScript + DOM) | React/Vue | Выбор команды; ноль рантайм-зависимостей, строгая CSP без `unsafe-inline` |
| LLM только для извлечения цели из текста | LLM-консультант или LLM в решении | Кредитное решение должно быть детерминированным и объяснимым; модель не может ухудшить основной путь |
| Документы в БД | Объектное хранилище | Достаточно для прототипа; интерфейс сервиса не изменится при переносе в S3-совместимое хранилище |

## 4. Ограничения и что дальше

| Ограничение | Следующий шаг |
|---|---|
| Подписание и выдача смоделированы | Интеграция с сервисом ЭП и АБС через тот же шаг `SIGNED → ISSUED` |
| Симуляторы источников | Реальные адаптеры за тем же интерфейсом `DataGateway`; кеширование ответов БКИ |
| Экспертная скоринговая карта | Статистическая модель с валидацией на дискриминирующую способность и стабильность; A/B-сравнение политик по версии |
| Нет KYC и регистрации клиентов | Онбординг через данные расчётного счёта и ЕГРЮЛ |
| Документы в БД, без антивируса | Объектное хранилище, антивирусная проверка, распознавание отчётности для автозаполнения выручки |
| Один процесс для всех продуктов | Разные маршруты по продуктам (залоговая экспертиза для инвестиционного кредита) как ветки машины состояний |
| Нет метрик воронки | Экспорт событий журнала в аналитику: конверсия по этапам, время до решения, доля автоматических решений (уже есть в `/api/analyst/stats`) |
